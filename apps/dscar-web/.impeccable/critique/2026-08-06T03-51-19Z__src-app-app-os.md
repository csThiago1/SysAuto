## Design Specificity Verdict

**LLM assessment:** Authored, but a patchwork core. The domain is genuinely present — the franquia (insurance deductible) settlement view splits what services/parts the client vs. the insurer pays for, `source_type` chips model the real insurer-estimate-vs-shop-complemento negotiation, insurer logos and plate-mono typography anchor every row, and "Na Oficina" as the default list filter matches the shop owner's actual mental model. But the detail workspace is two things bolted together: the `_v2` shell (header, stepper, nav rail, OverviewSection) is thoughtfully authored, while the tab bodies it composes (ServicesTab, ClosingTab, PartsTab) are reused v1 CRUD forms — the code's own comments admit this. The seam is visible in inconsistent card styling across tabs.

**Deterministic scan:** `detect.mjs` returned zero findings on `src/app/(app)/os` (exit 0, ~60 files scanned). No AI-slop markers triggered; nothing to reclassify as false positive.

**Visual evidence:** No live browser overlay — dev server fails to start. Both assessments independently found the same defects from screenshots: the horizontal status stepper is cut off at the right edge on every tab of the detail workspace (last stage truncated to "Fin"/"Fir"), and the Peças tab's totals table clips its "R$" values at the right edge with no visible scroll/fade affordance — both read as accidental overflow, not the app's own documented ScrollFade pattern. Older list screenshots (pre-restyle) show a since-fixed defect: a desktop table rendered on mobile with the SEGURADORA column cut off — confirms the restyle already closed that gap, not a live issue today.

## Overall Impression

The riskiest interaction in this whole app — moving an OS through a blocking status transition — is handled with real care: named hard/soft blocks, an override-request escalation for when the shop owner isn't at the desk, and a franquia breakdown that turns a confusing insurance calc into a readable "who pays what." What drags the score down is consistency, not concept: the v2 shell's polish doesn't extend into the tab bodies it wraps, "previsão de entrega" silently means two different fields depending on which screen you're looking at, and on mobile the detail workspace clips content (stepper, Peças totals) on every single tab. The single biggest opportunity: finish the v1→v2 migration for the tab bodies before adding anything new here — the shell has already set the bar.

## What's Working

1. **Blocked-transition UX** (`TransitionRequirementsPanel`) — enumerates hard/soft/warning blocks with distinct icons and colors, disables the action or offers a manager override with a clear escalation path, and shows a "pending override" pill. The app's highest-stakes interaction, handled with unusual care.
2. **Franquia settlement view** (`ClosingTab.tsx`) — renders a genuinely confusing insurance calculation as a plain-language "cliente paga / seguradora paga" breakdown. Domain expertise expressed as UI, not just data.
3. **MilestoneTimeline** — replaces a wall of datetime inputs with a done/pending timeline, a one-tap "Agora," and edit-on-demand; stays legible even at 390px.

## Priority Issues

- **[P1] "Previsão de entrega" reads different fields depending on the screen** — Why it matters: the OS list and its late-highlight logic read `estimated_delivery_date`, while the detail workspace's Overview tab reads `delivery_date` — the same label backed by two fields that can disagree, so an OS flagged late on the list can look on-time on its own page. Fix: pick one canonical field (`delivery_date`, matching CLAUDE.md's own definition) for both the list and Overview; relabel `estimated_delivery_date` as system-suggested. Suggested command: `/impeccable clarify`
- **[P1] Filling a milestone date silently changes the OS status** — Why it matters: `MilestoneTimeline`'s date fields (including the one-tap "Agora" shortcut) trigger a real status transition on save, disclosed only by a ⚡ icon with a hover `<title>` — undiscoverable on mobile, no confirm, no in-flow undo. A user backfilling a date can unintentionally jump the 17-status state machine. Fix: show the consequence as visible inline text on affected rows, and gate state-changing date fields behind the same confirmation the explicit "Avançar Status" action uses. Suggested command: `/impeccable clarify`
- **[P1] Mobile detail workspace clips content on every tab** — Why it matters: the horizontal status stepper is cut off at the right edge across all tabs (last stage truncated), and the Peças tab's totals table clips "R$" values at the edge with LÍQUIDO/CUSTO/MARGEM only reachable by an undiscoverable scroll — on a financial screen, silently-hidden totals are a real risk, not just cosmetic. Both independent assessments converged on this. Fix: apply this project's own ScrollFade pattern (already mandated in CLAUDE.md for exactly this situation) to the stepper and the Peças table. Suggested command: `/impeccable adapt`
- **[P2] Card/surface treatment inconsistent across tabs** — Why it matters: Overview/Dados use `rounded-xl border bg-card/50`, ClosingTab uses `rounded-xl border bg-muted/50`, ServicesTab uses `rounded-md border bg-muted/30` — the clearest visible marker of the v1/v2 seam, and it raises re-orientation cost tab-to-tab in a workspace users live in all day. Fix: extract one Panel/Card primitive (DadosWorkspace's `Panel` is a reasonable base) and apply it across ServicesTab, ClosingTab, and PartsTab. Suggested command: `/impeccable layout`
- **[P2] "Entrada" on Overview shows OS-creation time, not vehicle arrival** — Why it matters: the Overview "Prazos → Entrada" field renders `created_at` (when someone clicked "Nova OS") rather than `entry_date` (when the vehicle actually arrived) — these diverge whenever the OS is opened before or after the car is physically on-site, quietly misinforming any aging judgment a manager makes from that screen. Fix: read `entry_date` with `created_at` only as a fallback. Suggested command: `/impeccable clarify`

## Persona Red Flags

**Alex (Power User)**: Advancing an OS end-to-end bounces across Overview → Dados → Peças → Serviços → Fechamento repeatedly, with no keyboard shortcut to advance status and no bulk operations anywhere on the list or workspace. The fastest control in the UI — the one-tap "Agora" milestone shortcut — is also the most dangerous one (see P1), which is exactly backwards for a power-user affordance.

**Riley (Stress Tester)**: The header's "pendências" count derives only from `allowed_transitions[0]`, so with multiple allowed next transitions the count can silently mismatch whichever target the user actually selects. A screenshot shows an OS at "Pronto p/ Entrega" status while still carrying "4 pendências" and an incomplete services total — the delivery CTA correctly blocks in that state, but it's worth confirming the backend can never reach `ready` while hard blocks are outstanding. The date-fill-triggers-transition coupling (P1) can also leave a card with "date set but status didn't move," with no visible reconciliation UI.

## Minor Observations

- Fechamento's orange "Reparo concluído — há pendências…" warning text is crammed into a narrow column beside the green "Registrar Entrega" button on mobile, wrapping to ~6 short lines — should stack vertically at 390px instead.
- The sticky detail-workspace header runs roughly 200px tall on a 390px viewport before any tab content renders — heavy for a workspace this tab-dense.
- `FiscalEmissionModal` is imported and conditionally rendered on `showNfseModal`, but nothing ever sets that state to true (billing routes through `BillingModal` instead) — dead code that will mislead a future maintainer, not a user-facing issue.
- Desktop filter bar uses native `<select>` elements with default browser chevrons sitting next to a custom search input and a styled status pill — a minor visual-consistency mismatch, not a defect.
- The mobile OS list card (post-restyle) is a model of this codebase's own CLAUDE.md conventions — no border, `rounded-[11px]`, 3px left status stripe, `font-mono tabular-nums` — worth treating as the reference the detail-workspace tab bodies should converge toward.

## Questions to Consider

- Does the shop owner ever need to *record* a milestone date without wanting to *advance* the OS (e.g. backfilling, corrections)? If yes, coupling the date field to the status transition is a bug, not a feature.
- The v2 shell is clearly more polished than the v1 tab bodies it wraps — is finishing that migration already on the roadmap, or is "authored shell + CRUD guts" the permanent state? The card-consistency issue won't close until that's decided.
- Eight top-level sections is a lot for a phone screen used on a shop floor — is every one of them (e.g. "Estoque" as its own OS section) earning its place, or is it there because a component already existed?
